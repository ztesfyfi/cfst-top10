# CFST TOP10 项目升级方案

> 本文记录截至 2026-11-06 已确认的升级需求与架构决策，并作为实现验收基线。Docker 第一阶段代码已提交：容器骨架、Bearer Token、SQLite 来源持久化、TXT 来源管理、合并预览及 CFST 执行 API 已进入实现；功能是否可用以 README 和 GitHub Actions 实际验证结果为准。URL 来源仍未完成；手动测速状态/阶段信息及容器内间隔、每日定时调度代码已加入，待 CI 验证；Gist/Cloudflare Worker-KV 发布代码已提交，待真实账号联调验收。

## 1. 项目目标与范围

将现有 CFST 优选 IP 脚本升级为可通过浏览器管理的完整测速系统，同时保留 CloudflareSpeedTest（CFST）作为底层测速引擎。

主项目仓库：`ztesfyfi/cfst-top10`

本阶段只规划和改造主项目。Cloudflare Worker 采用独立部署单元（`cloudflare-worker/`），主应用通过 HTTPS Bearer Token 上传到 Worker，再由 Worker 写入 KV；Worker 部署及 Cloudflare 资源配置仍由用户自行执行。最终交付形态确定为 Docker 化应用，以 Docker Compose 作为正式且唯一的部署方式，不再提供 Bash 宿主机安装/运行方案。

目标能力：

- Web 管理面板：仪表盘、IP 来源管理、测速管理、结果与日志、发布管理、定时任务管理。
- 支持手动测速、停止测速、实时进度与日志展示。
- 支持 IPv4、IPv6，支持 TOP N、零丢包筛选及下载速度排序。
- 本地持久化配置、来源、测速结果、任务状态和日志；应用以 Docker 容器运行。
- 支持自动定时测速及按任务配置自动发布。
- 结果可发布到 GitHub Gist、Cloudflare Workers KV，或同时发布到两者。
- 不再把 SSH/SCP 上传到另一台 VPS 作为新版本的结果发布方案。

## 2. IP 来源管理

### 2.1 来源类型

系统管理三类独立来源：

1. 项目自带 IP 库；
2. 用户上传的 TXT 文件；
3. 用户配置的 URL 远程来源。

规则：

- 没有启用任何自定义 TXT/URL 来源时，项目自带 IP 库作为默认测速来源。
- 配置了自定义来源后，项目自带库、TXT、URL 可以同时参与测速。
- 用户可以关闭项目自带库，只使用自定义来源。
- 关闭自带库仅代表本轮不使用，绝不能删除本地自带 IP 库。
- 多个 TXT 文件和多个 URL 来源应可同时配置。
- IPv4、IPv6、混合地址列表均应支持。

### 2.2 来源管理操作

每个来源支持新增、编辑、删除、启用/停用、手动刷新。来源配置及用户 TXT 文件需持久化，服务重启后保留。

URL 来源应支持定时/手动获取。获取失败时保留最近一次成功缓存，不得用空响应覆盖有效缓存。面板中对 URL 敏感参数进行隐藏；编辑时支持取消，保存和删除操作需要二次确认。

### 2.3 测速前合并

每轮测速开始前：

1. 按任务所选来源读取已启用的数据；
2. 下载或读取各来源内容；
3. 校验 IP/CIDR 格式，统计无效条目；
4. 合并来源并去重；
5. 生成本轮临时测速输入文件；
6. 将临时文件交给 CFST。

合并过程不得覆盖项目自带 IP 库、用户原始 TXT 文件或 URL 缓存。面板应显示各来源条目数、合并前总数、重复数、无效数及最终测速数量。

## 3. 测速引擎与结果

- 继续使用 CFST 作为实际测速引擎，不另造测速内核。
- 支持 IPv4、IPv6 分开测速，也允许按任务设置执行范围。
- 支持手动开始和停止任务。
- 面板实时显示任务状态、执行阶段、当前协议、候选数量、已完成协议、运行耗时、日志和错误信息。CFST 未提供可靠百分比时不显示伪造百分比。\n- 手动任务与定时任务必须共用同一个 EngineManager 互斥执行器；运行中禁用重复启动，停止时终止 CFST 子进程。\n- 容器重启时将中断中的任务标记为 interrupted，不覆盖上一份有效结果。
- 支持设置 TOP N；默认值可沿用 10，并允许用户修改。
- 支持零丢包过滤，并按下载速度从高到低排序。
- 结果在 VPS 本地保存，IPv4、IPv6 结果分开管理。
- 测速失败、结果为空或结果校验失败时，不得覆盖上一份有效结果。
- 手动任务与定时任务调用同一套测速引擎和结果处理流程。

## 4. 定时任务

面板支持新增、修改、删除、启用/停用定时任务。每个任务至少包含：

- 任务名称；
- 执行规则：每天、每周、指定日期、固定小时数间隔或 Cron 表达式；
- 自定义执行时间；
- 测速 IP 协议范围（IPv4、IPv6）；
- 本次使用的 IP 来源；
- 测速完成后是否自动发布，以及发布目标。

面板显示上次执行时间、下次执行时间、最近执行状态及结果摘要。当前版本范围为间隔执行与每日执行，不引入周计划、指定日期或 Cron 表达式。

任务调度必须有互斥控制，避免多个测速任务同时操作 CFST 或覆盖临时文件。VPS 重启后应恢复已启用的任务。单个任务失败只记录自身错误，不得阻止其他任务。需要考虑从旧版每天 03:30 cron 任务平滑迁移，避免重复执行。

## 5. 发布架构：GitHub Gist + Workers KV

### 5.1 已确认的选择

新版本采用两条相互独立的发布路线：

- GitHub Gist；
- Cloudflare Workers KV。

不采用 R2 作为第一版存储后端。当前结果是小体积、读多写少的纯 TXT 文件，KV 足以满足预期用途；未来如数据规模或一致性要求发生变化，再评估增加 R2。

两条路线不是串联依赖关系，可以单独启用，也可以同时启用：

| 发布模式 | 行为 |
| --- | --- |
| 仅 Gist | 只发布到 GitHub Gist |
| 仅 KV | 只通过 Worker 写入 Workers KV |
| 双发布 | 分别发布到 Gist 和 KV，独立记录结果 |

任一后端失败，不得导致本地测速结果丢失，也不得回滚或破坏另一后端已成功发布的结果。

### 5.2 文件格式

发布内容不是代理订阅、YAML 或 Base64，而是普通 TXT：

- `ipv4.txt`
- `ipv6.txt`

默认每行一个 IP，使用纯文本格式。IPv4 与 IPv6 分开生成、分开发布、分开更新、分开记录状态。

### 5.3 发布操作与状态

- 支持测速完成后按任务配置自动发布。
- 支持面板手动发布已有结果。
- Gist 与 KV 分别配置、分别启停。
- IPv4 与 IPv6 可以分别发布。
- 每个文件独立记录最近成功时间、当前状态和错误信息。
- 发布失败可重试；失败时保留远端上一次成功版本。
- 已发布结果应独立于 VPS 在线状态：VPS 离线后，外部仍可读取最后一次成功发布的文件。
- 发布时只上传测速结果 TXT，不上传原始 IP 库、来源 URL、用户配置、日志或管理面板数据。

### 5.4 统一发布接口

主项目的测速核心不应直接耦合 Gist 或 Worker 的实现细节。建议定义统一发布适配层，由不同后端分别实现上传、更新、状态查询和错误处理。双发布模式下两个后端独立执行并分别报告结果。

已实现 `app/publish.py` 发布适配层：Gist 使用 GitHub Gist API PATCH，Cloudflare 使用 Worker 的固定文件 PUT 路由；支持单独发布、双发布、状态持久化和测速成功后的可选自动发布。Worker 源码在 `cloudflare-worker/`，KV Binding 固定为 `CFST_RESULTS`，上传 Secret 为 `CFST_UPLOAD_TOKEN`。仍需通过 CI 和真实账号联调验证。

## 6. Web 管理面板

面板至少包含：

- **仪表盘**：服务状态、当前任务、候选 IP 数、最终结果数、最近测速时间、发布状态。
- **IP 来源**：管理自带库开关、TXT 文件、URL 来源及刷新状态。
- **测速管理**：开始/停止测速、协议选择、TOP N、零丢包条件、进度和日志。
- **结果管理**：分别查看 IPv4/IPv6 结果，下载 TXT，查看历史结果。
- **发布管理**：选择 Gist/KV/双发布，查看每个文件的发布状态，手动重试。
- **定时任务**：任务增删改查、启停、执行历史及下次运行时间。
- **系统设置**：本地存储、面板访问、安全及日志配置。

面板应使用服务端 API，不允许浏览器直接持有 GitHub Token、Worker 上传密钥或其他后端凭据。

## 7. 安全与可靠性

- 管理面板必须有身份验证；默认仅监听本机地址，远程访问建议通过 SSH 隧道或可信反向代理。
- GitHub Token、Worker 上传密钥等敏感值不得写入公开仓库、前端代码或普通日志。
- URL 来源需要 SSRF 防护：限制协议、阻止访问环回/内网/链路本地及云元数据地址，并限制重定向、响应体大小和超时。
- 对导入内容执行严格 IP/CIDR 校验和数量限制。
- 文件更新采用临时文件加原子替换；失败时保留旧文件。
- 测速任务和定时任务需要互斥锁及明确的状态恢复机制。
- API 对请求体大小、路径、权限和输入内容进行校验。
- 更新程序不得覆盖用户自定义来源、缓存、历史结果和密钥。
- 卸载程序不得默认删除用户数据；删除数据必须明确提示并要求确认。
- 日志中不得输出 Token、完整敏感 URL 或私钥。

## 8. Docker 化与部署方式

### 8.1 正式部署原则

- 最终版本只支持 Docker 容器化部署，Docker Compose 是正式且唯一的安装、启动、停止和升级入口。
- 不再维护 Bash 宿主机安装器、宿主机运行菜单或依赖宿主机 crontab 的部署路径。
- 旧版 Bash 安装脚本仅作为历史版本兼容入口；在 Docker 版本完成并通过验收前，不应提前删除导致现有用户失去可用版本。正式切换时，README 和发布页面应明确标记旧方式退役。
- 不要求用户在宿主机安装 Python、Cron、CFST 等应用运行依赖；这些依赖由镜像负责。
- 提供可直接使用的 `docker-compose.yml`、`.env.example`、`Dockerfile`、`.dockerignore` 和中文部署说明。

### 8.2 镜像与容器

- 镜像至少支持 `linux/amd64` 和 `linux/arm64`，并在 CI 中分别构建和验证。
- 容器内包含 Web 前端、后端 API、CFST 引擎、来源管理、任务调度和发布适配器。
- 默认使用普通 Docker bridge 网络，不强制 `network_mode: host` 或 privileged。只有在真实测速和网络测试证明必要时，才增加最小化的额外网络权限，并说明原因。
- 容器默认以非 root 用户运行；确需访问特定资源时采用最小权限。
- Compose 服务设置合理的重启策略（默认 `unless-stopped`）、健康检查和日志轮转。
- 提供清晰的端口映射配置，管理面板默认不应无保护地暴露到公网。

### 8.3 持久化与运行时数据

- 使用 Docker named volume 或用户指定的宿主机 bind mount 持久化应用数据。
- 持久化内容至少包括：应用配置、项目自带 IP 库（可更新但不能因停用来源而删除）、用户 TXT 来源、URL 来源配置与最近成功缓存、IPv4/IPv6 测速结果、结果历史、任务定义与执行状态、发布状态及必要日志。
- 本地部署模式下，发布凭据存放在 Docker 持久化卷配置文件；认证后的本地管理面板会读取并预填凭据，输入框默认使用 password 遮罩。不要将面板直接暴露到公网。
- 临时测速文件、下载临时文件和运行中间产物放在容器临时目录，不能污染原始来源或正式结果。
- 容器重建、镜像升级或宿主机重启后，持久化数据必须保留。
- 提供备份与恢复说明；卸载 Compose 服务时默认保留数据卷，删除数据必须由用户显式确认。

### 8.4 调度与生命周期

- 定时任务调度器运行在应用容器内部，不依赖宿主机 crontab；支持固定小时数间隔与每日指定时间。
- 容器重启后自动恢复已启用任务，并通过持久化任务状态、分布式/进程锁或等效机制避免重复执行。
- 手动测速与定时测速共用同一执行器和互斥机制。
- 容器停止时应能妥善终止测速子进程，避免孤儿进程和半写入结果。
- 更新流程使用新镜像重建容器，持久化卷不变；支持回滚到前一镜像版本。

### 8.5 Compose 操作体验

部署文档应覆盖以下标准操作：

```bash
docker compose up -d
docker compose logs -f
docker compose pull
docker compose up -d
docker compose down
```

上述命令属于用户在宿主机管理 Docker Compose 的操作，不是项目 Bash 安装器。项目不应要求用户通过 `curl | bash` 或 `wget | sh` 安装应用。

同时提供健康状态检查、配置更新、备份、恢复和安全卸载步骤。

## 9. 兼容与迁移

- 评估并尽量兼容现有 `~/CFST` 目录、CFST 二进制及原有配置。
- 提供从旧版 Bash 安装目录迁移到 Docker 持久化目录的工具或清晰步骤；迁移前备份，迁移成功前保留旧数据和回滚条件。
- 旧版 SSH/SCP 发布只作为旧版本现状记录；新架构不再以其作为发布目标。
- 旧版每天 03:30 cron 任务需要识别并迁移为容器内任务，避免宿主机旧 cron 与容器调度器重复执行。
- 迁移完成后，宿主机旧 cron 项应由用户确认后停用；迁移程序不得未经确认删除旧数据。
- 最终 Docker 版本不再提供 Bash 安装/运行菜单；旧版脚本仅在过渡期保留，不作为新版本支持路径。
- Docker 及 Compose 的最低版本、存储权限和受支持主机平台应在实现和测试后明确，不得未经验证就宣称兼容所有 NAS/OpenWrt 环境。

## 10. GitHub 交付与开发顺序

主仓库后续交付应包括：

- 主程序、Web 面板及后端 API；
- 多架构 Dockerfile、Compose 文件、环境变量示例及镜像构建/发布工作流；
- 备份、恢复、更新、回滚和迁移说明；不再交付新的 Bash 宿主机安装器；
- 中文 README、配置说明、Docker 部署说明和旧版迁移说明；
- 单元测试、接口测试、来源合并测试、任务调度测试、发布适配器测试及 amd64/arm64 镜像验证。

建议开发顺序：

1. 重新审查现有仓库和实际运行逻辑，确定兼容边界；
2. 设计应用架构、容器运行用户、配置结构、数据目录和来源管理；
3. 实现来源读取、校验、合并、去重；
4. 整理统一测速执行器、结果处理和历史记录；
5. 实现容器内任务调度与互斥；
6. 实现 Web API 和管理面板；
7. 实现 Gist、KV 发布适配器及双发布状态处理；
8. 编写 Dockerfile、Compose、健康检查、持久化、备份/恢复和多架构构建；
9. 完成安全审查、自动化测试、容器生命周期测试和文档；
10. 提供旧版数据迁移路径，正式切换为 Docker Compose 唯一部署方式。

当前开发仅在 GitHub 仓库内进行代码和 CI 构建验证；不连接 VPS，不替用户部署 Cloudflare Worker，不创建或配置用户的 KV Namespace。
